# Security

## Posture in one line

There is **no cloud credential in this repository**, and the database password
never exists in a file a human or a CI log can read.

## Identity and credentials

| Boundary | Mechanism | Why not the alternative |
|---|---|---|
| CI → cloud | **OIDC federation** — GitHub Actions exchanges a short-lived workload token for a role. | A long-lived access key in repository secrets is the single most commonly leaked cloud credential. |
| Pod → cloud | **IRSA** (AWS) / **Workload Identity** (GCP), passed to the chart as an opaque annotation map. | A mounted service-account key file gets copied, committed and never rotated. |
| Pod → database | Password generated by Terraform, written to the cloud secret store, resolved in-cluster by External Secrets, which **templates `DATABASE_URL`** into a Secret. | A `terraform output` password lands in state, in CI logs, and in the values file. |

The consequence worth stating: the password is **not a Terraform output**.
Terraform exports only a *reference* (`arn:aws:secretsmanager:...` /
`projects/*/secrets/*`). Anyone reading the state file, the plan, the pipeline
logs or the Helm values sees the reference, never the value.

## Workload hardening

Every container in the chart runs with:

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001            # 101 for nginx
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }
```

Writable paths are explicit `emptyDir` mounts, nothing more. This is what caught
the nginx `/tmp` issue during deployment — the read-only root filesystem is
doing real work, not decorating the manifest.

## Network

- **Default-deny NetworkPolicy**, then only the paths the app needs: ingress →
  frontend, frontend → backend, backend → DNS/Postgres/443. Written with
  CIDR and port rules rather than cloud constructs, so it applies unchanged on
  any CNI that enforces policy.
- **The database has no public IP** on either cloud, and lives in private
  subnets reachable only from the cluster's security group / VPC peering.
- **Nodes are private**, egress via NAT.
- **Postgres requires TLS** (`?ssl=require` in the assembled DSN).

## Browser-facing

nginx sets, on every response:

```
Content-Security-Policy: default-src 'self'; img-src 'self' data:;
  style-src 'self' 'unsafe-inline'; object-src 'none';
  frame-ancestors 'none'; base-uri 'self'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
```

`default-src 'self'` is why the icon set is hand-rolled inline SVG and the fonts
are the system stack: a CDN would be blocked outright. The CSP shapes the
frontend rather than being bolted onto it.

One real bug here: `add_header` inside a `location` block **replaces** all
inherited headers instead of merging, which silently dropped every one of these
on HTML responses. It is now a `$uri` map so all `add_header` directives stay at
one level. Verified with `curl -D`, not assumed.

## The AI attack surface

This is the part most AI-in-CI designs get wrong, so it is worth being explicit.

**The model's output can never become a command.** `plan-command` has the model
select entries from a typed [operation catalogue](../ai/aiops/commands.py) and
fill validated parameters; the catalogue renders `argv`, executed with no shell.
The worst a confused or injected model can do is pick a *wrong allowlisted
operation with valid parameters* — it cannot add a flag, reach a shell, or name
an operation nobody put in the catalogue. `pr-1;rm -rf /` fails the
Kubernetes-name validator.

**Evidence is treated as untrusted input.** Container logs can contain a request
body written by an attacker. The gate's system prompt says so, the evidence is
fenced, and — the load-bearing part — the destructive cases are decided *before*
the model is consulted. There is a
[fixture](../ai/tests/fixtures/prompt_injection.json) whose logs instruct the
model to report the deployment healthy; the test asserts the release is still
rolled back.

**Findings without evidence are dropped.** A verdict citing no excerpt is
discarded, because an unsupported claim is what a hallucination looks like.

**Four controls on ChatOps**, not one: commenter must have write access; the
operation must be in the catalogue; parameters must validate; destructive
operations need explicit approval. One rejected step invalidates the whole plan.

## Supply chain

- Pinned dependency versions; `npm ci` against a committed lockfile.
- Multi-stage builds — no compilers or package managers in the runtime images.
- Image tags are **immutable content digests** (`sha-<commit>`) in cloud
  environments; only the local `:local` tag is mutable.
- The AI layer's dependencies are three packages (`anthropic`, `pydantic`,
  `PyYAML`).

## Gaps, stated plainly

- **`api_authorized_networks` defaults to `0.0.0.0/0`** — the Kubernetes API
  server is reachable from anywhere. It is the first thing to narrow before real
  use, and the tfvars comment says so.
- **No image signing or SBOM.** No cosign, no provenance attestation.
- **No secret rotation automation.** Terraform generates the password once;
  rotating it is manual.
- **No runtime security.** Nothing watches for anomalous process or network
  behaviour inside a pod.
- **`style-src 'unsafe-inline'`** is required by the current styling approach; a
  nonce-based CSP would be stricter.
- **No penetration testing.** The controls above are reasoned from the
  manifests and, where stated, verified by observation — not by an adversary.
